# Catalog and public history

The catalog records who researches what, which keys they sign with, and which
products exist. `history/` holds free past quarters. Both are plain JSON and
Markdown data, checked by `public-pilot catalog check`.

## Files

### `catalog/themes.json`

```json
{"format": "public-pilot-themes-v1", "themes": [THEME, ...]}
```

| Field | Contract |
| --- | --- |
| `theme_id` | Identifier, unique in the file |
| `title` | 1–200 characters |
| `geographies`, `policy_ids` | 1–100 distinct entries of 1–100 characters, as in a payload |
| `status` | `researched`, `in_progress` or `committed` |
| `author_ids` | Authors listed in `authors.json` |
| `product_ids` | Products in `catalog/products/` whose `theme_id` is this theme |
| `committed_on` | Date the theme was committed to, `YYYY-MM-DD` |
| `latest_public_quarter` | Latest `YYYY-QN` under `history/` for this theme's products, or `null` if there is none |

### `catalog/authors.json`

```json
{"format": "public-pilot-authors-v1", "authors": [AUTHOR, ...]}
```

Each author has `author_id`, `display_name` (1–200 characters) and `keys`, a list
of 1–50 keys. Each key has exactly:

| Field | Contract |
| --- | --- |
| `key_id` | Identifier, unique across the catalog; readers' trust files use it |
| `public_key` | Canonical standard base64 of the raw 32-byte Ed25519 public key, exactly as `keygen` prints it; unique across the catalog, so a key can never be listed twice under different IDs |
| `fingerprint_sha256` | SHA-256 of those 32 raw bytes, lowercase hex, as `public-pilot fingerprint` prints it |
| `status` | `active`, `retired` (no longer signs, still verifies past editions) or `revoked` (not trusted; treat revocation as final) |
| `valid_from` | UTC date from which the key is the author's, `YYYY-MM-DD`; it cannot change once listed. A product's editions may not predate the earliest `valid_from` among its author's keys for it |
| `packages` | Products of this author that the key may sign |

The file is **append-only**. Authors and keys are appended at the end; a key's
`status` may change and products may be appended to its `packages`. Nothing is
deleted, reordered or otherwise edited. Continuous integration enforces this
against the base branch of every pull request (see
[Changes relative to the base branch](#changes-relative-to-the-base-branch)).

### `catalog/products/<product_id>.json`

| Field | Contract |
| --- | --- |
| `format` | `public-pilot-product-v1` |
| `product_id` | Identifier; the file is named `<product_id>.json` |
| `theme_id`, `author_id` | A theme that lists this product and this author |
| `cadence` | `quarterly` |
| `universe_size` | Typical number of companies assessed per edition, 1–100 |
| `methodology_summary` | 1–5,000 characters describing the method in public terms |
| `public_history_path` | `history/<product_id>` |
| `review_status` | `author_published`, the only value for now: editions are published by their authors and not yet independently reviewed |

A product publishes all its editions under one package ID equal to its product
ID, so a reader's engine replaces one quarter's edition with the next.

`catalog/` holds exactly these files. Every document is strict JSON with no
unknown members; JSON Schemas for each are in `schemas/`.

## Public history

Each past quarter of a product lives in `history/<product_id>/<YYYY-QN>/` and
holds exactly five files:

| File | Content |
| --- | --- |
| `edition.snapshot.json` | The signed snapshot of the edition, with `purpose: demo` |
| `evaluation.json` | The signed evaluation: scores, ranks, decisions and weights |
| `REPORT.md` | The readable report, for example from `public-pilot render-evaluation` |
| `account.fixture.json` | A fictional account for `preview --offline`, with quotes for every target |
| `release.json` | The signed inventory of the other four files |

Published history is **append-only**: an edition's content never changes, and
its directory is never removed unless all its signatures are by revoked keys,
as for an edition forged with an exposed key. After a key change, the author
re-signs each edition
with `public-pilot resign-edition DIR NEW_DIR --key FILE --key-id ID`, which
writes a copy whose snapshot, evaluation and release are signed with the new
key and whose payloads, `REPORT.md` and `account.fixture.json` are unchanged;
the copy then replaces the directory. [SECURITY.md](../SECURITY.md) describes
the whole procedure.

An edition ID appears only once in a product's history. `history/INDEX.md`
lists every edition. It is generated by `public-pilot history index`; its
`Expired` column is evaluated when it is generated, so regenerate it after an
edition expires, or add editions only once they have expired.

## Checks

`public-pilot catalog check [DIR]` (default `.`) proves:

1. every catalog file has the required structure;
2. every fingerprint matches its key;
3. every reference resolves: themes, authors, products, keys' packages,
   history directories and `latest_public_quarter`;
4. every edition under `history/` resolves in historical mode, was published
   no earlier than the first `valid_from` among its author's keys for that
   product (whatever their status now), and has each of its three signed
   documents signed by one of those keys that is not revoked. A key listed
   later than an edition may therefore sign it, which is how an author re-signs
   past editions after replacing a key, or adds an edition published before
   the change. History editions are verified with
   trust that never allows paper trading, so they must have `purpose: demo`;
5. in every history directory, `evaluation.json` passes the `verify-evaluation`
   checks against `edition.snapshot.json`, and `release.json` passes the
   `verify-bundle` checks.

The output lists each edition with `expired`. Bundle hashes only prove that
files are unchanged; step 5 proves that the evaluation belongs to its edition. A
directory whose release is correctly signed can therefore still fail the
catalog check.

### Changes relative to the base branch

`public-pilot catalog check [DIR] --base BASE_DIR` also compares the catalog
and history with a base tree, such as an export of a pull request's base
branch:

1. `catalog/authors.json` only appends to the base file, as described above;
2. an edition directory of the base keeps the same snapshot payload,
   evaluation payload, `REPORT.md` and `account.fixture.json`; only its
   signatures, and with them the release inventory, may change;
3. an edition directory of the base may be missing only if every one of its
   signatures was made with a key that the catalog now lists as revoked. That
   is how an edition forged with an exposed key is withdrawn.

The output gains `"append_only": true`. For every pull request, a separate
continuous-integration job runs this command with the base branch's code
against the pull request's files. It reads them as data and never installs or
runs the pull request's code, and it compares with the merge base, so a branch
that is behind its base is not mistaken for one that deletes editions. A pull
request that changes these rules or the file formats is judged by its base's
rules until it is merged, so change code and data in separate pull requests.

### Trust files and the index

`public-pilot catalog trust [DIR] --product ID --out FILE` writes an engine trust
file for one product from the catalog. Revoked keys are left out. `allow_paper`
is `false` unless `--allow-paper` is given, and even then only `active` keys may
trade on paper. The output file is never overwritten.

`public-pilot history index [DIR]` regenerates `history/INDEX.md` from verified
editions and lists each edition with `expired`; with `--check` it changes
nothing and fails if the committed file differs.

All three commands are offline and read-only, apart from the files they are
asked to write.
